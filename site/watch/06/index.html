Field note 06 · George · brisk · en-GB

Redact the value. Keep the finding.

A claim can be public without the secret that proved it. This note covers replacement at the source, the limits of a blur, and the edges that leak.

format narrated MP4voice George · briskbase en-GBsource REA-20261121-afd06c73-83835

What this note covers

  • What a redaction replaces.
  • Why a blur is not enough.
  • The filenames, metadata and edges to check.

What it is not

  • No secret-shaped value is published.
  • No claim that redaction removes every risk.
  • No promise that a blur is safe.

Read the transcript

01
A finding can survive redaction.

A finding can survive redaction. The value can go. The observation stays.

02
Replace the value.

Replace the value at the source. Use a clear marker, such as redacted.

03
A blur is not a redaction.

A blur is not a redaction. The pixels, the metadata, or the file behind them may still be recoverable.

04
Keep the ID and locator.

Keep the ID and the locator. The reader still needs a route back to the evidence.

05
Check the edges.

Check the edges. Window titles, file paths, notifications and thumbnails can leak more than the main content.

06
Check the filenames.

Check the filenames and the alt text. A token in a filename is still a token.

07
Search the output.

Search the generated output for known values and prefixes. Inspect images at full size, not in a thumbnail.

08
Omit the value. Keep the finding.

If in doubt, omit the value and keep the finding. That is the safer public file.

Check the source

Every spoken line points back to the published record. The hash is a receipt, not a guarantee that every claim is correct.
